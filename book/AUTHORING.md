# 教学章节编写规范

本文件约束 `book/src/versions/` 中的版本主线。版本快照仍然是可独立构建的
checkpoint；教学章节负责把快照拆成读者能够逐步完成的学习路径。

## 读者闭环

每个版本都必须让读者走完以下闭环：

1. **学习任务卡**：说明前置版本、新增 Rust 概念、预计产出和非目标；
2. **先预测再运行**：给出最小 Lua 输入，让读者先写预期结果；
3. **实现难点**：把语言现象拆成数据、状态、所有权和失败边界；
4. **Rust 推导**：从一个不足或无法通过编译的写法推导到本版设计；
5. **代码阅读地图**：按调用顺序列出文件、类型和函数，不把目录列表当讲解；
6. **分段源码**：解释输入、所有者、可变状态、失败路径和输出；
7. **测试驱动**：至少把一个测试当作实现规格逐项阅读；
8. **三类练习**：理解题、实现题、调试题各至少一道；
9. **完成检查点**：列出不看答案也应该能解释或完成的任务；
10. **迁移与下一步**：明确临时设计在下一版如何保留、修改或删除。

`book_plan.md` 中的 14 项章节模板仍是内容合同。上面的十项是面向读者的呈现
顺序；相关内容可以合并到同一节，但不能省略。

## 内容预算

- 一次只引入一个核心问题；复杂版本用三级标题拆成 15–25 分钟的微课。
- 单个 `{{#include}}` anchor 最多 60 行。更长的函数必须增加更小的 anchor，
  或改为状态图、伪代码和完整源码链接。
- 每段核心代码前先说明“为什么需要”，之后说明“如何从测试观察”。
- 不用“显然”“简单”“同理”跳过所有权、生命周期、错误传播或状态变化。
- 首次出现的 Rust 概念必须解释；后续版本链接回首次解释，不重复整段语法教材。
- 练习必须说明修改范围、运行命令和可观察成功条件。

## 源码讲解清单

讲解一个类型或函数时，至少回答以下五个问题：

1. 输入数据来自哪里，采用值、共享引用还是可变引用？
2. 谁拥有长期数据，谁只临时借用？
3. 哪些状态会改变，改变前后必须保持什么不变量？
4. 哪些输入会失败，错误怎样到达 CLI 或调用者？
5. 用哪个测试或输出能够证明实现符合 Lua 合同？

## 自动检查

从仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/check_book_teaching.ps1
mdbook build book
node tools/check_book_links.mjs target/mdbook .
```

`check_book_teaching.ps1` 检查所有版本的必要教学环节、三类练习以及源码 anchor
长度。它不判断文章是否写得好，但会阻止章节退化回“几段介绍 + 一大块源码”。
