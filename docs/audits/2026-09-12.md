## 3. 问题明细

### A01 · P0：RuntimePartsMut 的安全接口允许对象借用期间回收，产生 use-after-free

位置：[runtime.rs](../../crates/lua_vm/src/runtime.rs) 第 2832、2873、5635 行；[lua_state.rs](../../crates/lua_vm/src/state/lua_state.rs) 第 282–292 行。

`parts_mut()` 安装了可以动态恢复 collector 的上下文，同时 `split_mut()` 把显式 `&mut GarbageCollector` 交给调用方。`state.with_gc_ref()` 的对象借用没有约束这个显式 collector，HRTB 只能阻止引用逃出回调，不能阻止回调内部通过另一个访问入口触发回收。

下列调用方代码全部是 safe Rust：

```rust
#![forbid(unsafe_code)]
use lua_core::table::Table;
use lua_vm::Runtime;

let mut runtime = Runtime::new();
let mut parts = runtime.parts_mut().unwrap();
let (state, gc, strings) = parts.split_mut();
let table = gc.create(Table::new());
state.with_gc_ref(table, |borrowed| {
    gc.collect(strings);
    println!("{}", borrowed.length());
}).unwrap();
```

Miri 默认 Stacked Borrows 和 Tree Borrows 均报错。为排除仅仅是实验性别名模型差异，又关闭 Stacked Borrows 检查运行同一程序，仍明确报告 `dangling reference (use-after-free)`。最终复验使用从项目 Cargo.lock 派生的依赖锁定，`thiserror` 为项目版本 2.0.18。

这是 **Rust 宿主 API 的安全性缺陷**；本次未证明任意 Lua 源码可以触发这条 UAF。

修复方向：明确分开初始化/显式 collector 借用和运行时动态服务上下文；不能同时保留两条可以独立解引用或回收的访问通道。对象 borrow 存在期间，类型系统或动态借用守卫必须阻止 collector mutation/sweep。

验收：上述调用应无法编译，或在回收前返回受控错误；实际公开 API 的正常路径通过 Miri。仅把对象临时加入 root 不足以修复两条访问通道的别名问题。

### A02 · P0：GC header 可由 safe 调用方改写，with_mut 还允许整体替换托管对象

位置：[header.rs](../../crates/lua_core/src/gc/header.rs) 第 90 行；[gc_object.rs](../../crates/lua_core/src/gc/gc_object.rs) 的 header 访问接口；[collector.rs](../../crates/lua_core/src/gc/collector.rs) 第 813、826 行；[mark.rs](../../crates/lua_core/src/gc/mark.rs) 第 79 行。

`GcObjectHeader::set_next` 是公开 safe 方法，并且仅要求 `&self`。调用方可从 `with_ref` 得到 header，然后把任意原始指针写进 collector 的侵入式链表：

```rust
gc.with_ref(table, |t| t.gc_header().set_next(16usize as *mut _)).unwrap();
gc.mark();
```

创建原始指针本身不需要 unsafe；Miri 在 `begin_mark_only` 中确认解引用无效地址。调用方测试启用了 `#![forbid(unsafe_code)]`。

另外，`with_mut` 注释称回调不能替换托管对象，但暴露的 `&mut T` 实际允许：

```rust
gc.with_mut(newer_table, |t| *t = Table::new()).unwrap();
```

两张无根表的探针结果为 `created=2 collected=1 remaining=1`：新 header 切断了旧节点链，collector 丢失遍历入口。正常 Drop 还可能因残留 side-table 条目触发断言。完整可运行探针位于 `target/audit-2026-09-12/safe_api_probe/`。

修复方向：GC header 的变更只能由 collector 控制；公开变更接口应提供受控 payload/对象操作，不能允许替换包含 header 的整个托管布局。还要验证异常展开时 barrier、容量记账与 header 不变量是否保持。

### A03 · P1：rawset 的 NaN 键使解释器中止，pcall 无法捕获

位置：[base.rs](../../crates/lua_stdlib/src/base.rs) 第 588–605 行；[table.rs](../../crates/lua_core/src/table.rs) 第 131–138 行。

```lua
print(pcall(rawset, {}, math.sqrt(-1), 1))
```

| 引擎 | 结果 |
|---|---|
| Rust Debug、Release | `table index is NaN` panic，随后 `panic in a function that cannot unwind`；进程退出 -1073740791 |
| 固定 C++ | pcall 返回 false 和 NaN 键错误，进程退出 0 |
| 官方 Lua | pcall 返回 `false, "table index is NaN"`，进程退出 0 |

`rawset` 检查 nil 键，却没有拦住 NaN；`Table::set` 的 panic 穿过 `extern "C"` 边界导致中止。此问题由普通 Lua 代码触发，不依赖资源耗尽。

修复方向：Lua 可达错误必须在 callback 内转换为 Lua 错误对象；检查同类标准库路径是否直接调用会 panic 的底层操作。验收必须使用子进程，覆盖 Debug、Release、pcall/coroutine，并确认错误后仍能执行下一条脚本。

### A04 · P1：os.time 极端输入导致 Debug 中止、Release 静默整数回绕

位置：[os.rs](../../crates/lua_stdlib/src/os.rs) 第 63、443–450 行。

```lua
print(pcall(os.time, {year=1e300, month=1, day=1}))
```

Rust Debug 在日期换算中整数乘法溢出，穿过 C callback 后中止进程；Release 返回 `true, -62198750016`。固定 C++ 返回受控的整数表示错误，官方 Lua 返回 `true, nil`。

修复方向：在浮点转整数之前检查有限性、整数表示范围和字段约束；日期运算使用受检算术。这里两个 oracle 的失败返回本身不同，应按项目已有双 oracle 决策制度登记目标行为；无论选择哪个目标，Rust 都不能发生宿主 panic 或静默回绕。

### A05 · P1：删除当前哈希键后 next 从头开始，重复返回已遍历的键

位置：[table.rs](../../crates/lua_core/src/table.rs) 第 368–413 行，尤其第 408 行。

```lua
local t = {a=1, b=2, c=3}
local k1 = next(t)
local k2 = next(t, k1)
t[k2] = nil
local k3 = next(t, k2)
print(k1 == k3)
```

Rust Debug/Release 输出 true；固定 C++ 和官方 Lua 都输出 false。探针不依赖三种实现恰好采用相同的哈希遍历顺序。

原因是删除时移除位置索引，随后 `next` 对不存在的 key 无条件调用 `next_hash_from(0)`。循环体只删除部分键时，会重复处理前面保留的条目。

修复方向：保留足够的删除后迭代位置，区分合法的已删除当前键与无效 next 键。验收覆盖部分删除、全部删除和前面保留条目的情况；不能仅验证“最终表变空”。

### A06 · P1：同一哈希键反复写入/删除，空表仍持续增长

位置：[table.rs](../../crates/lua_core/src/table.rs) 第 163–166、202–210 行。

插入不存在的 key 总是向 `hash_order` 追加；删除只把槽位改成 Nil，同时移除 `hash_positions`，没有复用或压缩旧位置。

```lua
local t = {}
collectgarbage("collect")
local before = collectgarbage("count")
for i=1,100000 do t.x=1; t.x=nil end
collectgarbage("collect")
print(next(t)==nil, collectgarbage("count")-before)
```

Rust Debug/Release 均报告空表、增加 3072 KiB；固定 C++ 增加 0.375 KiB，官方 Lua 增加 0.0390625 KiB。独立 Table 探针还确认：live entries 为 0，`get_size()` 从 192 增至 3,145,920 bytes。因此结论有实际容器容量证据，不能仅归因为三种实现 GC 计数口径不同。

这是仍然可达对象的内部容量积累，强制 GC 无法回收它。长寿命缓存、注册表和反复更新的状态表会受到影响。

修复方向：结合 A05 设计可复用墓碑或安全的压缩/重建策略。验收应检查固定大小活跃 key 集合在多轮 churn 后达到容量稳态，并保持删除迭代语义。

### A07 · P1：除零被转换成 Lua error，与两个 oracle 均不一致

位置：[execute.rs](../../crates/lua_vm/src/execute.rs) 第 5811–5819 行。

```lua
print(pcall(function() return 1/0 end))
```

Rust 返回 `false, "attempt to divide by zero"`；固定 C++ 和官方 Lua 都返回 `true, inf`。这是结果和控制流差异，不能通过调整错误位置或打印格式解决。

修复方向：先建立浮点语义矩阵，再改 DIV/MOD 分支；覆盖正负零、NaN、正负无穷以及编译期折叠/运行期运算的一致性。本次直接复现的是 DIV；MOD 的显式除零拒绝分支也需要单独验证，不能从 DIV 探针推导全部数值语义。

### A08 · P1：标准库混淆缺省参数与错误类型，并把原始参数当错误对象返回

位置：[string.rs](../../crates/lua_stdlib/src/string.rs) 的 `number_arg`、第 157、182、231、334 行函数；其他库有类似 `return -1` 风格，需逐项核查。

| 探针 | Rust Debug/Release | 两个 oracle |
|---|---|---|
| `pcall(string.find, "abc", "a", {})` | `true, 1, 1` | false + 参数类型错误 |
| `pcall(string.byte, "abc", {})` | `true, 97` | false + 参数类型错误 |
| `pcall(string.char, 256)` | `false, 256` | false + 越界错误字符串 |
| `pcall(string.gsub, {}, "a", "b")` | `false, "b"` | false + 参数类型错误 |

`Option` 参数解析把缺省、nil 和错误类型混在一起；部分失败分支只返回 -1，没有压入正确的 error object，VM 因而取得原先的栈顶参数。

修复方向：复用有明确结果类型的参数检查与 Lua error 构造，不要逐函数补字符串。验收矩阵应覆盖缺省/nil、错误类型、可转换字符串、范围、返回个数及错误对象类型。

## 4. 架构、性能和交付方向

六个 crate 的分层、Runtime 统一拥有 Heap 与 StateArena、对象身份校验、publication、错误隔离和双 oracle 工具值得保留。本轮证据不支持推倒重写编译器或 VM。

主要结构性风险是：`runtime.rs`/`execute.rs` 单文件非常大，动态服务上下文、显式 collector、C callback 与各种 continuation 交错。先收敛状态访问和错误合同，再沿 scheduler、native continuation、debug/trace 和 opcode 语义边界逐步拆分，拆分时以已有 trace 保持行为。

自动 GC 路径在 `runtime.rs:3197` 传入 10,000，`incremental_collection.rs` 因此在一个安全点完成整个周期；Atomic 又存在全量 rescan/drain。已有显式增量 step 不等于自动 GC 已有暂停时间上界。修复 A06 后，应测量长寿命大表、闭包/协程、分配密集脚本的峰值内存与 GC 暂停分布，再决定如何分摊自动周期。本轮没有给出未经基准验证的性能倍率。

allocator ledger 的 live/peak/total 是记账，尚不能替代内存配额和可恢复 OOM。若目标转向外部脚本嵌入，预算、取消和 IO/process capability 需要成为明确 API 合同；这些属于已规划的后续能力，而非本次新发现的隐藏功能缺失。

教学快照应继续保持独立版本语义。生产 Runtime 的安全修复是否回移某个教学版本，应明确记录，而不是简单将所有快照自动同步成同一套代码。
